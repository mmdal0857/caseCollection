# 모듈 패키징과 소비 인터페이스

## Question

추출된 코어는 어떤 형태로 존재하는가(독립 레포? 파이썬 패키지? 데이터 익스포트 CLI?) 그리고 정적 웹 게임 빌드는 이를 어떻게 소비하는가(빌드타임 JSON 익스포트 등 — Python 코어 ↔ JS 게임의 언어 경계 처리). 여기서 결정된 절차가 일반화 추출 플로우 스킬의 골격이 된다.

## Resolution

2026-07-20, 그릴링 세션(MMDAL × Opus). [OUT 코어 경계](06-core-boundary.md)·[웹 스택과 디바이스 타깃](05-web-stack.md)을 입력으로 패키징·소비 인터페이스 확정.

**코어의 형태 (b)**: 추출 코어 = **자기완결 파이썬 패키지**. caseCollection 레포 안에 두되 **게임 코드 import 0**(L 유지 — 재사용성의 증거). 물리적 레포 분리(독립 레포)는 2번째 소비자/모더 생태계가 실제로 설 때 승격하며, 그 승격 절차 자체가 플로우 스킬에 기록된다. n=1에 독립 레포 오버헤드(CI·버전관리)는 회피.

**인터페이스**: 패키지는 **CLI/엔트리포인트**로 **generic 코어 팩**(JSON)을 방출한다 — clue_type·case_pattern·story·work + frontmatter 엣지 + cleaned_texts. **게임 무관**(카드 스키마·슈트·문맥 태그를 모름, L). Python↔JS 언어 경계는 **파일 기반 JSON**이 공용어.

**빌드 체인 2단**:
- **① 코어 파이프라인 (스펙 ②)**: 원문 → wiki-agent → 위키 데이터 → CLI → **generic 코어 팩**.
- **② 게임 변환 파이프라인 (스펙 ①)**: generic 코어 팩 → 카드 재작성(04) + 문맥 태그 추출(14) + case 생성 → **게임 데이터**.
- 문맥 태그 추출(14)이 **LLM·빌드타임**이라 플레이어 런타임에 못 돌므로, 게임이 로드하는 팩(base/mod 공통)은 **변환 완료 "게임 데이터 팩"**이다. 모더는 ①+②를 **오프라인**으로 돌려 팩을 만들고, 게임은 로드 시 LLM 0.

**빌드 결합 (ii) 분리**: 두 파이프라인은 **오프라인**(저자 머신/전용 content-CI)에서 실행 → **게임 데이터 팩(JSON)을 커밋/릴리스** → **순수 JS(Vite) 빌드가 커밋된 팩을 읽음**. 웹 빌드 파이썬·LLM 의존 0(05 정적 배포 — GitHub Pages·itch butler 유지). 생성(LLM 느림·유료)은 콘텐츠 바뀔 때만. 팩 = 버전된 데이터 아티팩트(diff·롤백·재현 용이). base 팩 = 커밋된 공식 팩, 모드 팩 = 외부 로드 — **동일 포맷·단일 로드 메커니즘**([외부 데이터 팩 로드](16-external-data-pack-loading.md)). 팩 재생성+커밋 자동화(content-CI)는 후속 ops 사안.

**플로우 스킬 골격** (destination ② "일반화된 추출 플로우"): *위키-프로젝트의 IN 모듈을 자기완결 패키지로 추출 → CLI가 generic 데이터 팩 방출 → 하류 소비자가 변환·번들, 웹 빌드는 순수(분리 아티팩트).* 이 절차가 스펙 ② 작성 시 스킬로 문서화된다.

**낳은 것**:
- **[외부 데이터 팩 로드](16-external-data-pack-loading.md)** 프론티어 진입 — 로드 대상 = "게임 데이터 팩"(변환 완료), base=커밋 아티팩트·mod=외부, 동일 포맷. 팩 물리 포맷 세부는 16이 이어감.
- **스펙 ② 결정 관점 거의 완결** — 경계(06) + 형태·인터페이스(07) 확정, 플로우 스킬은 스펙 작성 단계로 폴딩.

## Comments

- 2026-07-21 [문맥 태그 의미론 확정](12-context-tag-semantics.md)의 파급 — **빌드체인 ②단계(게임 변환)에 "엔진 기계 검증" 스텝이 추가된다.** 위 결정의 ②단계는 "카드 재작성 + 태그 추출 + case 생성"이었는데, 12에서 생성물이 만족해야 할 제약이 **기계 판정 가능**하다는 게 확인됐다(03의 이중 제약: 풀 수 있음 + 정답이 이야기로 성립함). 그래서 ②단계는 이렇게 된다:

  `sLLM 대량 생성 → **엔진 기계 검증** → LLM 취향 필터 → 게임 데이터 팩`

  검증기는 프로토([11](11-core-loop-prototype.md))의 **순수 모듈**이 그대로 승격된다 — `engine.ts`(솔버빌리티), `cardFitsSlot`·`scenario.ts`(서사 응집). 이는 순수 모듈이 게임 런타임뿐 아니라 **빌드 파이프라인의 검증기**로도 소비된다는 뜻이므로, 위 "웹 빌드는 파이썬 0" 결정과 함께 **모듈의 소비자가 둘**(게임 런타임 JS · 빌드 검증)임을 스펙 ②에 명시해야 한다.
