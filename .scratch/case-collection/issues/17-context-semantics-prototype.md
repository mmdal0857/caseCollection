# 문맥 태그 의미론 프로토타입

## Question

[문맥 태그 의미론 설계](12-context-tag-semantics.md)가 종이 위로 확정한 것이 실제로 재미있는가 — /prototype으로 검증한다. **12는 검증 0회다.** 03도 원래 종이 확정이었고 [코어 루프 프로토타입](11-core-loop-prototype.md)이 "반응 레이어가 비어 있다"는 최대 결함을 잡아냈다. 12는 그 과정을 아직 안 거쳤으므로, **스펙 작성 전에 이 티켓이 먼저다.**

기존 프로토(`prototype/core-loop` 브랜치, v9)를 출발점으로 삼는다 — 엔진·드라마투르기·시나리오 모듈이 이미 있으므로 12의 변경분만 얹으면 된다.

### 최우선 검증 — ⚠ 11과 12가 정면충돌할 수 있다

**11(v6)에서는 "배치 중 라이브 재해석이 재미 그 자체"라고 판단**했다. 카드를 옮길 때마다 의미가 바뀌어 읽히는 게 "용도의 다면성"이 눈에 보이는 순간이라고 봤고, 그래서 잠금을 제출 시점에 두는 (c)를 골랐다. **그런데 12(Q6)에서는 배치 즉시 잠금 쪽((b) 계열)으로 갔다.**

즉시 잠금이 실험을 막아 다면성을 숨겨버리면 12의 핵심 전제("용도의 다면성 발견이 재미")가 자기모순에 빠진다. 12는 이걸 "배치=수(手) 모델"(잠금이 앞으로 전파되어 해석 공간을 열고 닫음 → 포석 플레이)로 해소하려 했으나 **검증되지 않았다.**

→ **①즉시 잠금이 포석의 재미를 주는가, 아니면 실험을 막아 답답한가.** 이게 이 티켓의 1번 질문이다. 반증되면 잠금 시점을 11의 판단(제출 시)으로 되돌리거나 절충안(가늠 배치 vs 확정 배치)을 찾아야 한다.

### 나머지 검증 항목

2. **얼굴(facet) 다면성** — 한 카드가 여러 용도를 갖는 게 "발견의 재미"인가, 아니면 "뭐가 뭔지 모르겠다"인가. 얼굴 수는 몇 개가 적당한가(2 vs 3+).
3. **어휘 게이트 심화(보유 ≠ 앎)** — 해금된 얼굴만 쓰는 게 성장감을 주는가, 아니면 "가진 카드를 왜 못 쓰지"의 답답함인가. 게스트가 얼굴을 빌려주는 게 완충으로 충분한가.
4. **앞→뒤 단방향 + 연쇄 해제** — 앞 카드를 고치면 뒤가 전부 풀리는 게 긴장인가 좌절인가. 되돌리기 비용(주목)이 적정한가.
5. **가변축** — case마다 다른 축이 리플레이성을 주는가, 아니면 매번 새 규칙을 배우는 부담인가. 재사용 풀 6~8종이 적정 규모인가.
6. **등급형 실패 + 얼굴 잠김** — 은밀·신중 극단의 "실패 대신 얼굴 잠김"이 체감되는가(안전한 구석 없음이 실제로 느껴지는가). BAD 빈도 4~5런 1회가 맞는가.
7. **오답도 노트에 기록** — 줄 그어진 오답 해석이 "부끄러운 자산"으로 느껴지는가, 아니면 그냥 잡동사니인가.

### 부수 확인

- 12의 파이프라인 가정 검증: **엔진이 실제로 콘텐츠 검증기로 쓸 만한가** — 얼굴이 붙은 case를 기계가 "①풀 수 있음 + ②이야기로 성립함"으로 판정할 수 있는지 스모크로 확인([14](14-tag-extraction-promotion.md)·[07](07-module-packaging.md)이 이 가정 위에 서 있다).

반증되면 [12](12-context-tag-semantics.md)를 재개정한다(지도 갱신). 프로토 자산은 이 티켓에서 링크.

## Resolution

2026-07-23, 프로토 **v10** 완주 (MMDAL × Fable). 자산: `prototype/core-loop` 브랜치 v10 커밋(7cf36d0 + 콘텐츠 조정) — `facets.ts` 순수 모듈, 카드 20종 얼굴 2~3개, 잠금 시점 3모드 런타임 토글, 가변축 4종, `smoke.ts` A~E 기계 검증.

**총평: 반증 없음 — 12 전면 검증.** 사용자 플레이 판정:

1. **★ 잠금 시점 = 즉시 잠금(12안) 확정** — "포석의 재미 맞음." 11(v6)의 "배치 중 라이브 재해석이 재미" 판단은 **얼굴 선택 단계가 그 재미를 흡수**하면서 대체됐다(놓기 전에 이 카드가 무엇이 될 수 있는지를 읽는 순간이 곧 재해석). 11과 12의 정면충돌은 12의 승리로 해소. **/ 기각**: 가늠→확정 절충안, 제출 시 잠금(11안).
2. **얼굴 다면성 = 발견의 재미** — 카드당 얼굴 2~3개 규모에서 혼란 아님.
3. **보유 ≠ 앎 = 성장감** — 게스트의 얼굴 대여가 완충으로 충분.
4. **앞→뒤 단방향 + 연쇄 해제 = 긴장으로 작동** — 되돌리기 대가(주목 +1) 적정.
- 종합: **"재미있다 — 핵심 코어를 유지하면서 퍼즐들을 붙여나가고 시각화하면 재미있는 게임이 될 수 있다"** → 코어 동결, 확장 방향은 퍼즐 콘텐츠 추가 + 시각화([08 MVP 스코프](08-mvp-scope.md)·[13 카드 아트](13-card-art-pipeline.md)의 입력).

**기계 검증 (smoke A~E 전부 PASS)**:

- A. 잠금 3모드 모두 소프트락 없이 GOOD 완주 — 즉시 잠금이 진행을 막지 않는다.
- B. **엔진 = 콘텐츠 검증기 성립** — 4개 case 전부 "①아는 얼굴만으로 풀림(진행 상태 스냅샷 기준) + ②정답이 이야기로 성립(응집 full)"을 기계가 판정. [14](14-tag-extraction-promotion.md)·[07](07-module-packaging.md)이 딛고 선 가정 확인. 검증기 실체 = `smoke.ts`의 `checkSolvable`/`checkCoherent` + `facets.ts`의 `facetStatus`.
- E. 이웃 전파(앞을 [현장]으로 잠가야 [신분 위장]이 열림) 명세대로 작동.
- D. 되돌리기 연쇄 해제 + 주목 대가 명세대로 작동.
- C. **설계 결함 1건 발견·수정**: 초안에서 강압 얼굴 5개가 전부 비명백 얼굴(`facets[1+]`)이라 학습기에는 "죽는 방향 둘" 중 강압(수사반 붕괴)이 **도달 불가** — 어휘 게이트(12 §4)와 실패 설계(12 §7)의 충돌. 강압 얼굴을 스타터 어휘로 승격해 해소. **→ 12 보강: 생성 제약을 이중에서 삼중으로 — "③각 실패 방향은 스타터 어휘만으로 도달 가능해야 한다"**(콘텐츠 검증기 제약, case 생성기 소관).

**파급**: 03·04·12의 미검증분 전부 검증 → 지도 마커 갱신([검증+종이]·[종이] → [검증]). case 생성기 fog가 티켓화 가능해짐 → [18 case 생성 파이프라인의 형태](18-case-generator-shape.md) 신설. 프로토 순수 모듈(engine·facets·dramaturgy·scenario·persona·josa)의 스펙 입력 승격 권장 유지(11과 동일). CONTEXT.md에 "생성 제약(삼중)" 항목 신설.
