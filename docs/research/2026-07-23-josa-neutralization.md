# 조사(助詞) 정보 누출 방지 — 빈칸 퍼즐의 조사 중립화 관행 리서치

- **작성일**: 2026-07-23
- **조회일(모든 출처 공통)**: 2026-07-23
- **질문**: Golden Idol형 "빈칸 두루마리" 추리 게임(한국어 우선, Svelte 웹)에서, 슬롯에 하드코딩된 조사가 정답 카드명의 받침 유무를 노출(정보 누출)하고 문맥 조건부 정답에서는 저작 자체가 불가능해지는 문제를 어떻게 처리하는가? 유니코드 정본·표기 관행·소프트웨어 선례·게임 선례·타언어 동형 문제를 1차 소스로 확인한다.

## 배경 (이미 확정된 로컬 사실 — 재조사 대상 아님, 요약만)

- caseCollection의 추리문 조각(pieces)에 조사가 정적으로 박혀 있음("`___이 통로가 되었고`"). 이 때문에 (1) 조사(이/가·을/를·은/는·(으)로)가 정답 카드명의 받침을 노출해 문법으로 후보를 소거할 수 있고, (2) 정적 조사와 실제 정답 받침이 어긋난 문법 오류 4건, 특히 **문맥 조건부 정답 슬롯**(배경 상태에 따라 같은 슬롯의 답이 바뀌어 두 정답의 받침이 갈리는 경우)은 정적 조사로는 저작이 불가능함이 실측됨.
- 레포에는 이미 유니코드 음절 분해 기반 조사 선택 모듈(`josa.ts`: `(code-0xAC00)%28`, ㄹ 종성 예외 처리)이 있고 **반응 텍스트 생성에는 쓰이나 빈칸(슬롯) 렌더링에는 미사용**. (이상은 태스크 배경으로 확정 — 본 리서치에서 재검증하지 않음.)

## 요약 (핵심 발견)

1. `(cp-0xAC00)%28`로 받침(종성) 인덱스를 얻고 인덱스 0이면 받침 없음이라는 규칙은 **유니코드 표준 16.0 §3.12의 한글 음절 조합 알고리즘에서 직접 도출되는 정본**이다. ㄹ 종성 = 인덱스 8도 자모 코드로 확인됨((으)로 예외의 근거).
2. 숫자·로마자로 끝나는 단어의 조사는 유니코드에 규칙이 없고, 실제 라이브러리는 **발음 기반 매핑 테이블**로 처리한다(es-hangul의 알파벳→한글 발음표, i18next 프로세서의 숫자 발음 판정).
3. "이/가" 슬래시 병기는 **한글 맞춤법 문장부호 '빗금(/)' 규정("대응·대등·나열 어구를 묶을 때")으로 뒷받침**되나, "빈칸 뒤 조사를 은닉하려는" 용도로 규정된 공식 문헌은 없다. 괄호 병기 "이(가)"는 관용이며 국립국어원도 "명확히 규정된 바 없다"고 답변.
4. 소프트웨어 선례는 (a) 마커 토큰 후처리, (b) 함수 호출 두 형태. **Unreal Engine은 `{Arg}|hpp(은,는)` 조사 수정자를 엔진 공식으로 내장**. ICU MessageFormat은 조사 전용 기능이 없어 수동 `select` 분기만 가능. 인기 npm 라이브러리(josa.js, i18next 프로세서)는 오히려 **(으)로의 ㄹ 예외를 틀리게** 구현하고, es-hangul만 정확.
5. 골든 아이돌 한국어판(팬 한패·공식 Redux)조차 조사 완전 중립화 대신 **문장 재구성 + 조사를 정답 단서로 수용**하는 절충을 택했다(커뮤니티 서술). 타언어(영어 a/an, 프랑스어·독일어 관사)도 동형 누출 문제가 있으며, "표층 문법형은 데이터 확정 후 렌더 시점에 결정한다"는 일반화는 툴체인 설계에서 성립한다.

## 1. 유니코드 한글 음절 구조의 정본

**출처**: The Unicode Standard, Version 16.0.0, Chapter 3 "Conformance", **§3.12 "Conjoining Jamo Behavior"**, 하위 절 "Hangul Syllable Composition" / "Hangul Syllable Decomposition". <https://www.unicode.org/versions/Unicode16.0.0/core-spec/chapter-3/> (HTML 원문 직접 확인).

원문에서 확인한 상수(직접 발췌):

```
SBase = AC00₁₆   LBase = 1100₁₆   VBase = 1161₁₆   TBase = 11A7₁₆
LCount = 19   VCount = 21   TCount = 28   NCount = 588 (VCount * TCount)   SCount = 11172 (LCount * NCount)
```

- 조합 알고리즘: `SIndex = S − SBase`, `LIndex = SIndex div NCount`, `VIndex = (SIndex mod NCount) div TCount`, `TIndex = SIndex mod TCount`. 역으로 완성형 `S = (LIndex*VCount + VIndex)*TCount + TIndex + SBase` (원문에 "SBase + (LIndex * VCount + VIndex)…", "SBase + LVIndex + TIndex" 형태로 기술).
- **받침(종성) 판정의 정본**: `TIndex = (cp − 0xAC00) mod 28`. 표준 원문 주석: *"TBase is set to one less than the beginning of the range of trailing consonants, which starts at U+11A8. **TCount is set to one more than the number of trailing consonants** relevant to the decomposition algorithm: (11C2₁₆ − 11A8₁₆ + 1) + 1"* → 즉 **TIndex 0은 "종성 없음"을 위해 예약**되고, 1..27이 실제 종성. 레포의 `(code-0xAC00)%28 > 0` = 받침 있음 판정은 이 정의와 정확히 일치.
- **ㄹ 종성 = 인덱스 8** ((으)로 예외의 근거): 종성 자모 범위는 U+11A8..U+11C2, `TBase = U+11A7`. ㄹ 종성 자모는 `ᆯ`(U+11AF)이므로 `TIndex = 0x11AF − 0x11A7 = 8`. 표준의 종성 배열 순서(ㄱㄲㄳㄴㄵㄶㄷㄹ…에서 ㄹ이 8번째)와 일치. → "받침이 ㄹ이면 '으로'가 아니라 '로'"의 판정 기준.
- **숫자·로마자·기호로 끝나는 단어**: 유니코드 표준에는 이들의 조사 결정 규칙이 **없다**(한글 음절 블록 밖). 실무 관행은 §3에서 확인 — 라이브러리들은 **발음 기반 매핑 테이블**로 마지막 토큰을 한글 발음으로 치환한 뒤 그 발음의 받침으로 판정한다(구체 코드는 §3 참조).

## 2. 조사 병기 표기의 공식 관행 (국립국어원)

> 주: `korean.go.kr`의 온라인가나다 상세 페이지는 본문이 JS로 렌더되어 `curl` raw 취득이 실패(제목만 반환). 아래는 WebSearch가 표면화한 **국립국어원 공식 답변 텍스트**와 문장부호 해설 페이지를 근거로 하며, 각 QnA URL을 병기한다.

- **슬래시 병기 "이/가"의 규정 근거 = 한글 맞춤법 문장부호 '빗금(/)'**: 국립국어원 문장 부호 해설에 따르면 빗금은 *"대응하거나 대등하거나 나열되는(임의 선택) 둘 이상의 형태(어구)를 짝으로 묶을 때"* 쓴다. "이/가", "을/를"은 이 용례에 해당. 출처: 국립국어원 「문장 부호의 이해」 <https://www.korean.go.kr/nkview/nknews/200012/29_4.htm>.
- 한글 맞춤법 **부록(문장 부호) 빗금 설명의 실제 용례**로 *"( )이/가 우리나라의 보물 제1호이다."* 가 제시됨(온라인가나다 답변 인용). → 슬래시형 조사 병기는 공식 규범 문서에 용례로 존재.
- **괄호 병기 "이(가)"의 지위**: 국립국어원 온라인가나다는 소괄호가 "보충적" 성격이므로 소괄호 뒤 조사는 **앞말을 기준으로 호응**시키는 것이 일반적이라고 안내하나, 동시에 *"명확히 규정되어 있는 바는 없으며 단정적 답변을 드리기 어렵다"*고 반복해 답한다. 즉 괄호 병기 조사는 **관용일 뿐 강제 규정이 아니다**. 출처(온라인가나다 상세): qna_seq 316103(조사 괄호 사용법), 302384(괄호 뒤 조사의 쓰임), 296978(괄호 뒤 조사), 307419(괄호 사용 시 ~을/를), 294694(괄호 표기 후 조사 형태 변화) — 각 `https://www.korean.go.kr/front/onlineQna/onlineQnaView.do?mn_id=216&qna_seq=<seq>`.
- **결론(제약)**: "빈칸 앞/뒤 조사 병기"가 표준 관행인지에 대한 **직접 규정은 확인되지 않음**. 확실한 것은 "빗금 = 대등/나열 어구 묶음" 규범까지이며, 이를 빈칸 조사 은닉 용도로 차용하는 것은 규범의 파생 적용이다(가독성·관행 논거로 정당화해야 함). 괄호형은 공식 근거가 더 약함.

## 3. 소프트웨어의 동적 조사 처리 선례 (소스코드 = 1차)

### 3.1 JS / npm

- **josa.js (e-/Josa.js)** — raw: `raw.githubusercontent.com/e-/Josa.js/master/josa.js`, README 동 경로.
  - API: 후처리 함수형. `Josa.c('사과','을/를') → '를'`, `Josa.r('귤','이/가') → '귤이'`. 포맷 문자열로 조사 종류 지정.
  - 받침 판정: `_hasJong = s.charCodeAt(last) - 0xac00) % 28 > 0`. 지원 5종: 을/를, 은/는, 이/가, 와/과, **으로/로**.
  - **결함 1**: (으)로가 `_hasJong ? '으로' : '로'` — **ㄹ 종성 예외 미처리**(ㄹ받침 단어도 '으로'로 잘못 출력). **결함 2**: 완성형 한글만 가정 → 숫자/로마자/기호는 `(cp-0xAC00)%28` 음수 모듈로로 항상 "받침 없음"으로 오판.
- **i18next-korean-postposition-processor (Perlmint)** — raw: `raw.githubusercontent.com/Perlmint/i18next-korean-postposition-processor/master/src/{index,consts,testers/number,testers/hangul,modifiers/parenthesis}.ts`.
  - **마커 문법**: 번역 문자열에 `{{value}}[[를]]` 형태로 **이중 대괄호 `[[조사]]`** 마커를 인라인. i18next post-processor가 렌더 시 앞 텍스트(prevPart)의 받침을 보고 치환. 정규식 `/\[\[(?:을|를|이|가|은|는|(?:으로)|로|과|와|(?:이랑)|랑)\]\]/g`.
  - 지원 6종: 을/를, 이/가, 은/는, **으로/로**, 과/와, 이랑/랑. **testers 체인**(Hangul→Number→Kana): 결정 불가 시 다음 테스터로 폴백.
  - **숫자 처리 = 발음 기반 판정**(`testers/number.ts`): 마지막 숫자 1·3·6·7·8 → 받침 있음(일·삼·육·칠·팔의 종성 ㄹ/ㅁ/ㄱ/ㄹ/ㄹ), 2·4·5·9 → 받침 없음(이·사·오·구), 0(영)은 자릿수 단위(조·해·자·구·재 등 12/20/24/32/44자리, ≥52)까지 따져 판정. → **숫자 발음 매핑 테이블의 실증 사례**.
  - **modifiers/parenthesis.ts**: 괄호로 끝나는 경우(예 "홍길동(들)[[을]]") 괄호를 벗겨 앞말 기준으로 조사 판정 — 병기 뒤 조사 호응을 코드로 구현.
  - **결함**: `consts.ts`의 `["으로","로"]`도 `existFinal ? '으로' : '로'` 단순 이진이고 hangul tester는 종성 종류를 안 봄 → **(으)로의 ㄹ 예외 미처리**(josa.js와 동일 버그).
- **es-hangul (toss)** — raw: `raw.githubusercontent.com/toss/es-hangul/main/src/core/josa/josa.ts`, `src/_internal/constants.ts`, `src/core/hasBatchim/hasBatchim.ts`. (원조 `kimdhoe/josa` README가 유지보수 후속으로 es-hangul을 권장.)
  - API: `josa(word, '이/가')` → `word+조사` 반환(타입 레벨 템플릿 리터럴로 결과 타입까지 추론), `josa.pick(word, ...)` → 조사만.
  - 받침 판정: `hasBatchim` = `(charCode − 0xAC00) % 28 !== 0` (비한글이면 false 반환).
  - **ㄹ 예외 정확 처리**: `로_조사 = ['으로/로','으로서/로서','으로써/로써','으로부터/로부터']`, `disassembleCompleteCharacter(마지막글자).jongseong === 'ㄹ'`이면 index를 뒤집어 '로' 선택. 와/과도 뒤집음(받침 있음→과).
  - **로마자 대문자 처리**: `/^[A-Z]+$/`이면 `ALPHABET_TO_KOREAN` 표(A→에이, B→비, … L→엘, M→엠, N→엔, R→알, S→에스, …)로 마지막 글자를 한글 발음으로 치환 후 판정. → **로마자 발음 매핑 테이블의 실증 사례**.
  - 지원 14종(이/가, 을/를, 은/는, 으로/로, 와/과, 이나/나, 이란/란, 아/야, 이랑/랑, 이에요/예요, 으로서/로서, 으로써/로써, 으로부터/로부터, 이라/라).
  - **한계**: 숫자 전용 처리는 없음 — `hasBatchim`이 비한글에 false를 주므로 숫자로 끝나는 단어는 "받침 없음"으로 처리(i18next 프로세서의 숫자 테스터 같은 발음 판정이 없음).
- **API 형태 요약**: 두 패턴 — (a) **마커 토큰 후처리**(i18next `[[를]]`, kr-postposition `{은}` 스타일; 저작자는 문장에 조사를 인라인으로 두되 렌더 시 치환), (b) **함수 호출**(josa.c / es-hangul josa; 이름과 조사 종류를 코드에서 결합).

### 3.2 게임 엔진

- **Unreal Engine (엔진 공식 지원)** — Epic 공식 문서 "Text Localization in Unreal Engine" <https://dev.epicgames.com/documentation/en-us/unreal-engine/text-localization-in-unreal-engine> (인자 수정자/Argument Modifiers 절).
  - FText 포맷에 **한글 조사(Hangul post-positions) 수정자 내장**. 문법: **`{Arg}|hpp(은,는)`** (수정자 키워드 `hpp`). 값이 자음/모음으로 끝나는지에 따라 올바른 글자를 삽입("사람은"/"사자는"). 값 목록은 **[자음(받침 있음), 모음(받침 없음)] 순서**, 각 값은 선택적 따옴표 문자열.
  - 같은 인자 수정자 프레임워크에 복수(plurality)·성(gender) 수정자도 기본 제공. `ITextFormatArgumentModifier` 구현으로 확장 가능.
  - → **"조사 결정을 렌더(포맷) 계층에 두고 데이터 확정 후 자동 처리"의 엔진 레벨 산업 표준 선례.**
- **Unity**: 표준 내장 조사 기능 **공식 1차 문서 미확인(확인 불가)**. Localization(Smart Strings/SmartFormat) 또는 I2 Localization의 한국어 조사 처리는 서드파티/커뮤니티 확장에 의존하는 것으로 보이나, 엔진 공식 문서로는 확증하지 못함 → 정직하게 "Unity는 서드파티 의존, 공식 조사 수정자 미확인"으로 남김.
- **ICU MessageFormat**: 조사 전용 기능 **없음**. 내장 인자는 `select`/`plural`/`selectordinal`/`gender`뿐(ICU User Guide "Formatting Messages" <https://unicode-org.github.io/icu/userguide/format_parse/messages/>). 조사를 하려면 호출자가 받침 여부를 **별도 boolean으로 계산**해 `{hasFinal, select, other{을} no{를}}`처럼 **수동 분기**해야 하며, 문자열에서 자동 결정하지 못함. → **결론: ICU 자체로는 한글 조사 자동 처리 불가(수동 select만 가능).** (Smartling/Crowdin 등 ICU 도입 도구 문서에도 조사 자동 처리 언급 없음.)
- **Project Fluent (Mozilla)** — <https://projectfluent.org/>: `select` 표현식으로 임의 변수 분기가 가능하고 "번역 복잡도는 각 로컬라이제이션이 통제"한다는 철학. 조사 전용 내장은 없고, **문법형 선택을 로컬라이저(렌더 계층)에 위임**하는 설계. (보조 근거 — 조사 특화 API 아님.)

## 4. 퍼즐 게임의 직접 선례 — Golden Idol 한국어판

> 소스 신뢰도: 팬/커뮤니티 위키·언론 기사 위주(1차 스크린샷·번역자 인터뷰는 미확보). 슬롯별 조사 은닉 여부의 픽셀 단위 확인은 불가.

- **한국어 지원 연혁**: 원작 *The Case of the Golden Idol*은 출시 시 한국어 미지원 → 2023-02-04 팬 한패(오고루/이뉴엔도·엄바굼바 팀) 배포(fmkorea/gamemeca 기사). 이후 **Redux 업데이트(2024-10, 무료)에서 공식 한국어 추가**, 후속작 *The Rise of the Golden Idol* 및 시리즈도 공식 한국어 지원. 출처: 게임메카 <https://www.gamemeca.com/view.php?gid=1695357>, Steam 공지(Redux/Localization patch).
- **조사·빈칸 처리 방식(핵심 서술)** — 나무위키(커뮤니티 위키, 중신뢰) *The Rise of the Golden Idol* / *황금 우상 사건* 문서(WebFetch/raw는 403, WebSearch 표면화 인용):
  - 퍼즐 문장이 길어질수록 **조사(예: -에, -의)가 단서로 추가되어**, 미묘한 뉘앙스 차이가 정답/오답을 가르게 만들었고 어려운 구간의 번역이 어색해져 난이도가 상승.
  - 원작 애니메이션이 **영어 SVO 어순** 기준인데 한국어 퍼즐 문장은 **SOV 어순**으로 배치되어, 어순 차이에 익숙지 않은 한국 플레이어에게 혼란/선언문 같은 부자연스러움 유발. 번역자가 퍼즐 구조를 어순에 맞게 조정하지 않음.
  - 공식 번역보다 **팬 한패 품질이 더 낫다**는 평가.
  - → **해석(제약)**: 상업/공식 한국어판조차 "슬롯 조사 완전 중립화"라는 깔끔한 해법을 쓰지 않고, **문장을 조사가 자연히 붙도록 재구성**하거나 **조사를 정답 판별의 일부(단서)로 남기는** 절충을 택함. 즉 조사 중립화가 업계 자명 표준은 아니며, "조사를 의도적 단서로 쓸 것인가(난이도) vs 순수 중립화할 것인가"는 열린 설계 선택.
- **유사 한글 워드게임**: 꼬맨틀류는 "단어 하나의 의미 유사도" 맞히기라 **문장 슬롯 조사 문제가 발생하지 않음** → 직접 선례 아님. 문장형 빈칸(추리문)에 국한된 문제임을 재확인. (문장형 한글 빈칸 퍼즐의 조사 중립화 공개 사례는 **빈약/확인 불가**.)

## 5. 타언어의 동형 문제 (관사·성)

- **영어 a/an (모음 시작 노출)**: 시험 문항 작성 문헌에서 **"문법적 단서(grammatical cue)"는 회피 대상**으로 명문화. 어간(stem)과 문법적으로 안 맞는 보기는 소거 가능해 타당도를 훼손하므로, "모든 보기는 어간에서 문법적으로 자연스럽게 이어져야 한다"는 원칙이 표준. 클로즈 문항에서 빈칸 앞 'an'을 노출하면 정답이 모음으로 시작함을 누출("He saw ___ elephant"). 출처: AJPE "Best Practices Related to Examination Item Construction and Post-hoc Review" <https://www.ajpe.org/article/S0002-9459(23)01572-3/fulltext>(및 PMC 미러 PMC6788158), NCSU "Best Practices for Creating Multiple-Choice Questions", JB Learning ch.5 "Selected-Response Format". **관행적 회피법**: "a/an" 또는 "a(n)" 병기 — 영어권도 조사와 동일하게 **병기로 문법 단서를 무력화**한다.
- **프랑스어 le/la/l', 독일어 der/die/das (성·모음 노출)**: 관사가 성(gender)과 모음 여부를 노출하는 동형 문제. 다만 크로스워드/클로즈 작법의 **1차 문헌은 미확보(확인 불가)**. 원리(문법 일치 단서가 답의 속성 노출)는 영어 a/an과 동일하게 적용됨.
- **"언어별 관사/조사 결정은 렌더러 책임"이라는 일반화의 성립 여부**: **성립한다.** 근거 — Unreal이 조사(hpp)·성·복수를 **인자 수정자로 렌더 계층에 두고**, Fluent가 `select`를 **로컬라이저에 위임**하며, ICU가 `select`로 **분기를 포맷 계층에 두는** 것은 모두 "표층 문법형(조사·관사·성·수 일치)은 값이 확정된 뒤 렌더 시점에 결정한다"는 동일 설계 원칙의 구현. 단 차이는: **Unreal만 한글 조사를 자동(hpp)으로** 결정하고, ICU/Fluent는 자동이 아니라 저작자가 분기를 명시해야 함.

## 시사점 (플랜 입력)

- **받침 판정 코어는 재발명 불필요·외부 의존 위험**: `(cp-0xAC00)%28` + ㄹ=8 예외는 유니코드 16.0 §3.12에서 도출되는 정본이며, 레포 `josa.ts`가 이미 그 정본(종성 종류까지)을 갖췄다. 반면 인기 npm(josa.js, i18next-korean-postposition-processor)은 **(으)로의 ㄹ 예외를 틀리게** 구현 → 외부 라이브러리 채택은 오히려 회귀 위험. es-hangul은 정확하나 숫자 처리가 없음.
- **누출 원천 차단의 유일하게 일관된 해법 = "정답 확정 후 렌더 시점 조사 결정"**: 슬롯 자리에서 조사를 노출하지 않는 표면형이 필요. Unreal `hpp`가 그 산업적 선례(엔진 공식). 이 방향은 레포 `josa.ts`를 슬롯 렌더에 연결하는 것으로 무의존 구현 가능.
- **표면형 선택지(모두 근거 있음, 누출 차단 강도 순)**: (a) **렌더 시점 정답에서 조사 계산**(빈칸엔 조사 미표시, 저작자는 조사 태그만 명시 — Unreal hpp / es-hangul josa형) → 누출 0; (b) **슬래시 병기 "이/가"**(문장부호 빗금 규정으로 뒷받침되나 "대등 어구" 용도의 파생 차용, 시각적 잡음); (c) **괄호 병기 "이(가)"**(관용, 공식 규정 없음). 강도 (a) > (b) ≈ (c).
- **문맥 조건부 정답 슬롯은 (a)를 사실상 강제**: 정답 2개의 받침이 갈리는 경우 정적 조사·병기로는 여전히 애매하거나 둘 다에 부정확 → 렌더 시점 계산만이 각 정답에 정확. 이 케이스 하나만으로도 (b)/(c)는 부분해에 그침.
- **비한글 종결 카드명은 발음 매핑 테이블이 제약 조건**: 숫자·로마자·기호로 끝나는 카드명이 도메인에 있으면 순수 `(cp-0xAC00)%28`은 오판. 선례는 es-hangul `ALPHABET_TO_KOREAN`(로마자→발음)과 i18next `TestNumber`(숫자→발음). 카드명 도메인에 그런 표기가 실제로 존재하는지 점검이 선행 제약.
- **조사별·받침별 예외 존재**: (으)로(ㄹ 예외), 와/과(받침 시 과) 등은 "받침 유무" 이진만으론 부족하고 종성 자모까지 봐야 함. 레포 `josa.ts`·es-hangul은 처리, 단순 라이브러리는 실패 → 판정 로직은 종성 종류를 보는 수준을 유지해야 함.
- **완전 중립화는 업계 자명 표준이 아님(디자인 선택지 열림)**: 골든 아이돌 상업 한국어판조차 문장 재구성 + 조사를 단서로 수용하는 절충을 택함. 따라서 "조사를 의도적 난이도 단서로 남길지 vs 순수 중립화할지"는 게임 디자인 결정으로 열어둘 수 있고, 본 문제(누출)는 "중립화" 쪽을 택할 때의 제약이다.
- **병기형 채택 시 규범 근거의 한계**: 국립국어원 근거는 "빗금 = 대등/나열 어구 묶음"까지만 확실하고, "빈칸 뒤 조사 은닉"을 규정한 공식 문헌은 없음(확인 불가). 병기형을 UI 표기로 쓸 경우 정당화는 규범이 아니라 가독성·관행 논거에 의존해야 함.
